# Build Product vs Source Repository

## Why this matters

Some GitHub repos are **auto-deploy artifacts** — they look like ordinary static sites, but every commit is generated by a build bot from a separate source repo. Editing them directly produces work that gets overwritten on the next deploy. This reference is the diagnostic for "is this repo a build product?", and the playbook for finding the real source.

## The pattern

The cleanest case looks like:

```
<org>/docs          (private)         — VuePress source: package.json, src/*.md, .vuepress/, plugin/
<org>/pages         (public, GitHub Pages)
                                       ↑ Vercel auto-deploys "build output" → commits back here
```

`pages/` is just where Vercel pushes the rendered HTML so GitHub Pages can serve it. The author never edits it.

### Other common shapes

| Hosting platform | Source repo marker | Deploy commit message pattern |
|------------------|--------------------|--------------------------------|
| **Vercel**       | `vercel.json` with `"outputDirectory"` + `package.json` `"build": "..."` script | `Deploy from @<sha>` |
| **Netlify**      | `netlify.toml` `[build]` block + `_redirects` / `_headers` | `Deploy <id>` or `netlify-deploy <sha>` |
| **Cloudflare Pages** | n/a (config in dashboard) or `wrangler.toml` | `pages build` / `cf-pages-deploy` |
| **GitHub Actions + gh-pages branch** | `.github/workflows/<x>.yml` with `actions/deploy-pages` | workflow-generated commits on the `gh-pages` branch |

## How to detect a build-product repo (do this BEFORE editing)

### Cheap heuristics, run in order

```bash
# 1. List the root contents — does it look like rendered output, not sources?
gh api repos/<o>/<r>/contents --jq '.[] | .name + " " + .type' | sort
#   ↳ If the listing is mostly *.html + assets/ + sitemap.xml + robots.txt + 404.html
#     and zero markdown / package.json / _config.yml / *.toml: high confidence it's the build side.

# 2. Check commit messages for deploy-bot patterns
gh api repos/<o>/<r>/commits --jq '.[] | .commit.message' | head -20
#   ↳ "Deploy from @<sha>", "Deploy preview <id>", "pages build and deployment":
#     build bot, not human author.

# 3. Check the same org for a private sibling
gh api orgs/<org>/repos --jq '.[] | .name + " private=" + (.private|tostring)'
#   ↳ A private sibling named "docs" / "site-source" / "src" alongside the public "pages" / "site" / "www"
#     is the canonical source.

# 4. Confirm with package.json / build config on the suspected source repo
gh api repos/<o>/<suspected-source>/contents/package.json --jq '.content' | base64 -d | grep -E '"build"|vuepress|next|hugo|mkdocs|docusaurus'
#   ↳ "vuepress build src" / "next build && next export" / "hugo --minify" / "mkdocs build" /
#     "docusaurus build" in the build script: that's the source repo.
```

### Decision flowchart

```
Listing shows *.html + assets, no .md / package.json?
├── Yes → almost certainly build product. STOP and find the source.
│        (See "Finding the source repo" below.)
└── No (has package.json / *.md / _config.yml / etc.) → normal repo, edit as usual.

Commit messages match "Deploy from @..." / "Deploy <id>" / "pages build"?
├── Yes → deployment bot, not human commits. Same as above.
└── No (normal human commit messages like "fix: ...", "docs: ...") → normal repo.
```

## Finding the source repo

```bash
# Look at the org's other repos
gh api 'orgs/<org>/repos?per_page=100' \
  --jq '.[] | select(.name != "<this-repo>") | "  - " + .name + " (private=" + (.private|tostring) + ") desc=" + (.description // "<none>")'

# For each candidate, fetch package.json / .vuepress/config.ts and look for build scripts
# that consume *.md or *.mdx source files
```

The first thing to read on the suspected source repo is `package.json` → `scripts.build`. A build script that takes a markdown source directory as input (`vuepress build src`, `docusaurus build`, `hugo`, `mkdocs build`) confirms it.

## Why "just edit the rendered HTML" fails

| Issue | Detail |
|-------|--------|
| **Auto-deploy will overwrite** | The very next time the CI runs (often on push to source, or on a cron), the build pipeline regenerates HTML from current source. Your hand-edits get blown away. |
| **Reviewer pain** | Rendered HTML diffs are huge (5–10x the equivalent markdown), full of shiki inline styles, lang tokens, anchor `<a>` headers, ARIA attributes, and VuePress-specific comment markers. The actual prose change is buried. |
| **Drift** | The build product repo's history no longer matches the source repo. Next time someone clones the source and rebuilds, they get *different* HTML than what's checked in to the build product. |
| **Lost attribution** | Your commit author shows up in the rendered HTML repo's history but never makes it to the source repo where actual authors care. |

## What to do instead — the right path

1. **Identify the source repo** (private sibling, or single-repo with `src/*.md` and a build script).
2. **Open the PR against the source repo**, editing the markdown / source files.
3. **Let the auto-deploy handle the rest** — after the PR merges, the build pipeline regenerates HTML and pushes to the build product repo as a deployment commit (not your concern).
4. **Optionally**: also open a PR against the build product repo for the *immediate* HTML change, but mark it `[skip-deploy]` / `[ci-skip]` so the next deploy doesn't overwrite it. Realistically, just wait for the auto-deploy — it usually fires within minutes.

## When "edit the HTML" actually IS the right move

- The repo has **no build config at all** (no `package.json`, no `vercel.json`, no `netlify.toml`, no `_config.yml`, no GitHub Actions workflow) → it's hand-maintained HTML, probably an old GitHub Pages site. Edit it normally.
- The repo is the **only** repo for the project, contains markdown sources AND rendered HTML side-by-side, and the README explicitly says "edit the HTML here". Some orgs do this for legal/reproducibility reasons — they want the rendered output under version control too.
- You're doing **emergency hotfixes** to a live outage and waiting for a deploy cycle is unacceptable. In that case, edit both: the HTML for the immediate fix, then *also* fix the markdown source so the next clean deploy doesn't regress. Track both PRs and link them in the description.

## Quick sanity check before opening the PR

Ask yourself: "If I open this PR and it gets merged, will the next deploy still show my changes?"

- **Yes** → continue.
- **No** → wrong repo. Find the source and re-do the work there.
