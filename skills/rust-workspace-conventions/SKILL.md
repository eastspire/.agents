# Rust workspace convention migration

## When to Use

- Moving member crate dependencies up into root `[workspace.dependencies]` and converting members to `{ workspace = true }`
- Centralizing `[profile.dev]` / `[profile.release]` at the workspace root and stripping member profile sections
- Switching member `[package]` metadata (readme / edition / authors / license / repository / exclude) to `xxx.workspace = true` inheritance — **MUST drive every field from `[workspace.package]` set; `exclude` is the aggregated deduplicated union of every member's exclude list, not a per-member duplicate**
- Importing an external crate into the workspace (folding a single-repo crate into a monorepo via `cp -r` + squashed commit — ctares-style import, NOT `git subtree`)
- Any "make all Cargo.tomls follow the standard" pass over a Rust workspace

Migrating an existing workspace so members inherit from the root Cargo.toml. The RULES (edition 2024, dep-block ordering, profile values, exclude lists) are defined in the `rust-standards` skill §13 — load it first; this skill is the migration procedure and its pitfalls.

## Procedure

1. **Inventory before writing anything.** Parse every member Cargo.toml with Python `tomllib` and dump: per-member deps per section (`dependencies` / `dev-dependencies` / `build-dependencies` / `target.*`), shared deps (used by ≥2 members), version-spec conflicts, and inter-member (local) deps. Do not eyeball — workspaces hide conflicts.
2. **Build root `[workspace.dependencies]`:**
   - Local member deps: `name = { path = "<member-dir>", version = "<member's CURRENT package version>" }` — read the member's own `package.version`, do not copy the dependent's (possibly stale) requirement. **`version.workspace = true` is INVALID in `[workspace.dependencies]`** — that syntax is only legal inside `[package]`. Cargo rejects it with `invalid type: map, expected a string … in 'version'`. Heterogeneous workspaces (per-member `major.minor`) MUST use a literal version string here even though members use `version.workspace = true` internally — there is no shorthand.
   - Version conflicts across members: take the max requirement in root (caret reqs make this compatible).
   - Features: a feature EVERY user specifies goes in the root entry; a feature only some users want stays member-level as `dep = { workspace = true, features = [...] }` (member-level feature addition is allowed, root stays minimal).
   - Dev-deps on workspace members: check the publish interlock first (rust-standards §13.4) — a member used both as regular dep and dev-dep must keep the dev usage as a direct `path = "../x"` entry in the consuming member, NOT workspace-inherited.
3. **Rewrite members programmatically, never by hand.** Multi-line entries (features arrays, exclude arrays) break naive line-slicing. Replace each dep section wholesale from a spec dict, then assert with tomllib that the dep KEY SETS per section are identical before/after. For per-package metadata fields (`readme`/`edition`/`authors`/`license`/`repository`/`exclude`), see step 5 — these get swept separately into `[workspace.package]`, not handled here.

4. **Order every dep block** per rust-standards §13.7 round 3: local group alphabetic, ONE blank line, third-party group alphabetic. Applies to all 4 block types including `[workspace.dependencies]`.

5. **Sweep `[package]` metadata into `[workspace.package]`.** For every field that is identical across (or near-universal across) all members, lift it to root and convert each member to `xxx.workspace = true`. Field-by-field procedure:

   a. Candidate fields: `readme`, `edition`, `rust-version`, `license`, `authors`, `repository`, `description`, `keywords`, `categories`, `exclude` (the last is a list, not a scalar).
   b. Scalar fields (`readme`, `edition`, `license`, `authors`, `repository`): if all members currently use the same value, lift it to `[workspace.package]` and replace each member line with `<field>.workspace = true`. If even one member diverges, leave it and continue checking.
   c. **`exclude` (list) is special**: write the **deduplicated union** of every member's current `exclude` list into `[workspace.package]`. Order alphabetically for stable formatting. Then convert every member — INCLUDING those that previously had no `exclude` line — to `exclude.workspace = true`. A 4-entry baseline that matches only the most-common members drops entries the rare members rely on and silently changes their published archives (orphan `logs/`, `img/`, `debug/` dirs slip into the .crate; per-member `**/*.pid`, `uploads/` patterns disappear).
   d. Do NOT touch `name`, `version`, `description`, `keywords`, `categories`, `[lib]`, `[[bin]]` — these are per-member identity or product fields; they stay.
   e. Members that previously had no `exclude` line ARE NOT exempt from step 5c — they pick up the union by default. Forgetting them gives them a different effective exclude than their peers.

   **Field decision table — what to lift vs what to leave.** Run this check before touching anything in step 5:

   | Field | Aggregate? | Why |
   |---|---|---|
   | `name` | NO | Per-crate identity. Cargo rejects duplicate `name` in a workspace. |
   | `version` | NO if heterogeneous, YES only if all same | Cargo forbids two workspace members with the same `name + version`. Heterogeneous ctares-style workspaces (each member has its own `major.minor`) MUST keep per-member `version`. A homogeneous workspace can set `[workspace.package].version` once and let every member use `version.workspace = true`. |
   | `readme` | yes | All members share the same workspace README path. |
   | `edition` | yes | All members compiled under same toolchain. |
   | `rust-version` | yes | Same MSRV for the whole repo. |
   | `license` | yes | Whole repo under the same license. |
   | `authors` | yes | Whom to email on security advisories — repo-wide. |
   | `repository` | yes | The whole repo lives at one URL. Be aware: this flattens the per-member homepage on crates.io to the root repo URL (see pitfall below). |
   | `exclude` | yes (deduplicated union) | Published archives get the union — no member loses anything; members that lacked an exclude gain workspace defaults. |
   | `description` | NO | Per-crate marketing copy shown on crates.io / docs.rs. Aggregating makes `bin-encode-decode`'s blurb show on `jwt-service`. |
   | `keywords` | NO | Per-crate crates.io search terms. Aggregating mires every search result with unrelated tags. |
   | `categories` | NO | Per-crate crates.io browsing taxonomy (encoding / authentication / network-programming / ...). Aggregating puts unrelated categories on every package — `bin-encode-decode` would list under `web-programming` and `encoding` together, breaking crates.io's category filter. There is no `[workspace.package]` field that supports "default + member additions" — you cannot combine `categories.workspace = true` with member-local extras. |

   The litmus test for each field: **does aggregating make the package's per-crate discovery WORSE?** If yes, leave it per-member regardless of how uniform the values currently look across the workspace. A workspace where 21 of 22 members happen to share `categories = ["network-programming", "web-programming"]` is still not grounds to lift — that one outlier (`encoding` for `bin-encode-decode`, `authentication` for `china_identification_card`, ...) tells you the field is per-crate identity.

   The `exclude` exception is the one place aggregation is genuinely safe: a *larger* exclude can only remove files, never add files; no published package is hurt by the union, and members that previously had no exclude gain useful defaults.

   Do all 22+ members in a single Python pass that scans the regex block once per file and writes back; never hand-edit a 20-file diff (one missing substitution out of 60 will silently leave a member not inheriting).

6. **Profiles:** append `[profile.dev]` + `[profile.release]` (identical contents, values per §13.3) to the ROOT only, strip all member `[profile.*]` sections (§13.3.1 — cargo ignores member profiles with a warning). Verify each rewritten member with a git before/after tomllib comparison: only the `profile` key may differ.

7. **Verify, in order:**
   - `python3 <rust-standards skill>/scripts/verify_dep_order.py <repo>` — 0 violations across ALL workspace Cargo.tomls.
   - `cargo check --workspace` — must show zero `profiles for the non root package will be ignored` warnings AND zero `[E0432]` / unresolved-import errors (these surface when `*.workspace = true` references a field not present in `[workspace.package]`).
   - `cargo metadata --no-deps --format-version=1` parsed to compare each member's resolved `readme` / `authors` / `repository` / `license` against the root `[workspace.package]` values — confirms every member inherited, none held a hardcoded copy.
   - `cargo package --list -p <one member per exclude-distinct shape>` — sanity that nothing material changed for the publishing tarball.
   - `cargo test -p <most-depended member>` at minimum.

8. **Commit migrations as separate commits** from feature commits (e.g. `refactor: unify member dependencies into workspace dependencies`, `refactor: centralize build profiles at workspace root`, `refactor: lift member package metadata to workspace.package`) — do not amend them into an unrelated pending feature commit.

9. **Importing an external crate (ctares-style fold-in, NOT git subtree)** — when the workspace owner asks to fold a standalone repo into the monorepo (user preference: single squashed commit to master, no PR, no git subtree history), execute these steps in order. Each is a hard prerequisite for the next:

   a. **Copy + strip**: `cp -r <source-repo>/ <workspace>/<new-name>/` then `rm -rf <workspace>/<new-name>/.git/` immediately. The nested `.git/` directory breaks `cargo package --list` (causes orphan `.github/workflows/`, `Cargo.lock` etc. to slip into the .crate regardless of root `exclude`) AND confuses `git status` in the parent repo. Verify `find <new-name> -name .git -type d` returns empty.
   b. **Rewrite `Cargo.toml`** following the field decision table from step 5 and the third-party `dep = { workspace = true }` pattern. Drop the original `[profile.dev]` / `[profile.release]` (root owns profiles). Use the **literal version** of the new package (ctares: `10.1.7`) — NOT the source repo's prior version (e.g. `0.7.46` for `hyperlane-time`) — because the source repo's version history is discarded by the squashed-commit import.
   c. **Rewrite `src/lib.rs` first line**: `//! <crate-name>` MUST equal `[package].name` (rust-standards §2.4 / check 37). The source repo's header often opens with the OLD crate name (`//! hyperlane-time`); a quick edit can rename the package field while leaving the doc block stale, then `audit_rust_standards.py` will flag it on the next run.
   d. **Rewrite every `tests/<sub>/mod.rs`** that contains `use <old_name>::*;` (or `use <old_name>::SomePath;`) — tests are independent crates with their own dep graph and never benefit from the lib.rs `pub use` glob. Grep with `grep -rn 'use <old_name>' <new-name>/tests/` to find all hits. Also rewrite any sibling member's `lib.rs` that re-exports the renamed crate (e.g. `color-output/src/lib.rs` had `pub use hyperlane_time::*;` when `hyperlane-time` was folded into `system-time`).
   e. **Rewrite `README.md` badges**: every `https://img.shields.io/crates/v/<old_name>.svg` link, `https://docs.rs/<old_name>`, `https://github.com/<org>/<old_name>/workflows/...` URL, and `cargo add <old_name>` snippet. Per user preference, badges point at the new crate name and the GitHub Actions badge targets the monorepo (`<org>/<monorepo>/workflows/Rust/badge.svg`), not the defunct single-repo workflow.
   f. **Add to root `Cargo.toml`**: `members` list (one new entry) AND `[workspace.dependencies]` literal-version path entry (see step 2 — `version.workspace = true` is INVALID here). Then `cargo check --workspace` MUST exit 0 — if it doesn't, the most common cause is a missed `use <old_name>` in either `tests/<sub>/mod.rs` or a sibling member's `lib.rs` re-export, not the new crate itself.
   g. **Update root `README.md`** in lockstep: bump crate count, add rows to the layout block + packages badge table + crate origin table — three places, alphabetical by crate name. Verify the count by `ls -d <workspace>/*/Cargo.toml | wc -l` (matches `members.len()`).
   h. **Commit + push as a single squashed commit** to master (ctares user preference: no PR, no separate history commits). Verify the push with `git log -1 --stat` showing all expected files; if a file is unexpectedly modified, `git checkout -- <file>` and rerun.
   i. **Delete mirror copies of the OLD-named source repos on gitee/gitcode** before announcing completion. The mirror namespace that holds them is usually NOT the source org — for `crates-dev/ctares`, the mirrors live under `eastspire/<old-name>` (set up by the cross-platform mirror skill), not `crates-dev/<old-name>`. Probe both namespaces with a HEAD check per repo, then DELETE via API: `curl -X DELETE "https://gitee.com/api/v5/repos/<ns>/<name>?access_token=TOKEN"` and `curl -X DELETE -H "private-token: TOKEN" "https://gitcode.com/api/v5/repos/<ns>/<name>?access_token=TOKEN"`. Verify with a 200 → 404 probe cycle. GitHub-side deletion requires the user's PAT to carry `delete_repo` scope; if `DELETE /repos/...` returns 403 with `Must have admin rights to Repository`, hand off to the user (they do it manually in the web UI at Settings → Danger Zone).

   **Pitfall**: do NOT `git subtree add` for ctares — the existing 21 crates were imported via `cp -r` + squashed commits (see `crates-dev/ctares` log), and mixing subtree history with cp-r squashed commits leaves an inconsistent repo.
   **Pitfall**: per-subpackage `.github/workflows/*.yml` carried over from the source repo is **only dead code for the subpackages whose source repos are being deleted**. If 3 out of 24 subpackages are being folded from a defunct upstream, delete those 3 subpackages' `.github/` directories — the other 21 subpackages' `.github/workflows/` are still wired to their `crates-dev/<name>` upstream repos and remain valid. Don't over-delete by default; the user's phrasing "delete the github scripts of subcrates, useless" scopes to the set whose source repos are gone.

## Pitfalls

- **`cp -r <external-crate> <workspace>/<new-name>` carries the source's `.git/` directory.** The nested git repo breaks `cargo package --list` (causes orphan `.github/`, `Cargo.lock`, etc. to slip into the published .crate regardless of root `exclude` — a pre-existing cargo quirk that gets WORSE under nested-git conditions) AND confuses `git status` in the parent repo. Always `rm -rf <new-name>/.git/` immediately after the cp. Verify with `find <new-name> -name .git -type d` returning empty before the first `git add`.
- **`[workspace.dependencies]` rejects `version.workspace = true`** — only the `[package]` table accepts that syntax. Cargo's error is `invalid type: map, expected a string … in 'version'`. Heterogeneous workspaces that use `version.workspace = true` in each member's `[package]` STILL need a literal `version = "X.Y.Z"` in the root `[workspace.dependencies]` path entry — there is no shorthand. This is the most common stumble when first folding a third-party crate into the workspace; the fix is one extra keystroke (`version = "<root-version>"`) but the error message does not point at the schema rule.

- **`[workspace.members]` order is the publish order.** List members topologically — a member that publishes another member as a path/`workspace = true` dependency must come AFTER it. Alphabetical order silently breaks `cargo publish` sequencing and publish tooling that walks members in order (e.g. chunkify depending on file-operation must be listed later). Only path-only dev-deps (`dep = { path = "../x" }`, no version) are exempt — cargo publish strips dev-deps and skips their registry check; a dev-dep carrying a `version` field DOES constrain order.
- **Heterogeneous workspaces (no `[workspace.package].version`, members keep independent versions) need per-member version sync** — any sync/bump tooling must align each `[workspace.dependencies]` local entry to THAT member's own `package.version`, not a single root version, and must not error out just because no root version exists.
- **User layout preference: workspace members live directly at the repository root** (`<member>/Cargo.toml`), not under a `crates/` subdirectory. When moving, members referencing each other via `{ workspace = true }` are unaffected, but root `members` list, `[workspace.dependencies]` path entries, CI grep paths, and README layout docs all need the rewrite.
- **A crate that can never publish (e.g. name collision) must carry `publish = false`** so publish tooling skips it instead of failing the whole run.
- When verifying "no profile warnings", grep for `will be ignored`, not `profile` — `Finished \`dev\` profile [optimized]` matches `profile` and gives a false count of 1.
- A member that hardcodes `edition = "2024"` cannot switch to `edition.workspace = true` until the root `[workspace.package].edition` is raised (and `rust-version` to ≥1.85). Check that NO other member inherits root edition before raising it — members with explicit editions are unaffected.
- `cargo package --list -p <member>` is the ground truth that workspace metadata inheritance resolved (readme/authors/repository/exclude). A member README.md in its own dir still wins packaging when readme.workspace points outside the package dir — that is fine and matches published-crate behavior.
- Machine-local cargo mirror config (`.cargo/config.toml`), `Cargo.lock`, `target`, and test-generated `tmp/` fixture dirs must be gitignored, never committed — check `git status` before every amend when iterating on Cargo.toml changes; `git add -A` sweeps them in silently.
- **`repository.workspace = true` flattens every member's homepage/repo URL to the root repo URL.** After step 5, `cargo metadata` shows every member's `repository` resolving to whatever is in `[workspace.package].repository` (the root repo) — not the per-member crate's individual GitHub repo. If a workspace is a true monorepo where each member IS the root repo and crates.io shows `.../ctares`, this is fine and matches the user's preference of "one config toml". If the workspace is a federated group where each member has its own repo (e.g. each `crates-dev/X` lives in its own upstream), this migration silently drops those per-member URLs from crates.io listings. Confirm the user's intent for the crates.io homepage link before flattening.
- **`cargo package --list` shows `.github/workflows/...`, `Cargo.lock`, `.gitattributes` even when root `exclude` lists them all** when a subcrate directory is its own git repo (`<member>/.git` exists alongside the workspace `.git`). Cargo's `cargo package` uses `git ls-files` plus a dotfile heuristic that doesn't honor `exclude = [".github", "Cargo.lock"]` for git-backed path deps — this is a pre-existing cargo quirk (issues rust-lang/cargo#16267, #15409), NOT caused by workspace inheritance. Verify the migration is non-breaking by diffing `cargo package --list -p <member>` BEFORE and AFTER the metadata sweep: the only differences should be the `Cargo.toml.orig` line and possibly `exclude` field provenance. If `.github/` appears in the post-sweep .crate, that was already true before — not a regression.
- **`exclude` is NOT match-aware against the subcrate's own VCS** — patterns in `[workspace.package].exclude` follow gitignore-style globs against the SUB-CRATE directory only, not the workspace root. A pattern like `.github` in root exclude is meant to match `bin-encode-decode/.github/workflows/rust.yml` (it does, when iterated correctly) but does NOT match `/bin-encode-decode/../.github/...` (workspace root). For sub-package publishing, this distinction is fine because each member's git tree IS the unit of packaging. For release/distribution at the workspace level (e.g. `tar -czf ctares.tar.gz .`), you still need workspace-level `.gitignore` or `--exclude` flags.
- **`categories` / `keywords` / `description` look aggregate-able when 21/22 members share them — they aren't.** Apply the field decision table in step 5 BEFORE writing the migration script. Once the migration writes 22 files of `categories.workspace = true` pointing at a deduplicated 10-item list, the only safe rollback is to restore each member's original `categories = [...]` from git HEAD (the union operation is one-way). The user-visible failure mode after a wrong lift: `bin-encode-decode` shows up under `web-programming` and `encoding` together on crates.io; users browsing the `web-programming` category find `bin-encode-decode` and complain. The cost of asking first ("is `categories` per-crate marketplace taxonomy?") is one round-trip; the cost of writing then reverting is one churned diff. Same trap applies to `keywords` (per-crate search terms) and `description` (per-crate marketing blurb). The field decision table enumerates the rest.
- **`cc bump --patch` on a heterogeneous (no `[workspace.package].version`) workspace automatically enters mode 3 — every member +1 patch, preserving each member's `major.minor`**. So a workspace with `color-output@10.1.6` and `crate-cli@0.2.8` becomes `color-output@10.1.7`, `crate-cli@0.2.9`, and the root `Cargo.toml` gets `[workspace.package].version = "10.1.7"` added (matching the highest-after-bump). Don't pre-decide the bump target — let the tool's mode-3 result be the version you workspace-promote. The cascade also rewrites every `[workspace.dependencies]` path-member `version = "..."` ref to the new versions in the same pass — verify the post-bump diff includes both `[package].version` changes AND the dep-ref changes before commit. To make the workspace truly unified (every member `version.workspace = true` inheriting one root version) you need one extra step AFTER `cc bump`: convert each member's `version = "X.Y.Z"` line to `version.workspace = true`, then `cc sync` to rewrite the root `[workspace.dependencies]` refs. The intermediate state after the conversion but before `cc sync` will fail `cargo check` with "candidate versions found which didn't match: 10.1.7" — that is the signal sync has not run.
- **`cargo package` warns `readme` is `../README.md` when `readme.workspace = true` points to a file outside the member dir** (`README` is workspace-root, member is `<member>/README.md` sibling or absent). The packaged `.crate` still contains the workspace README correctly — the warning is informational. If you want silence, place a per-member `README.md` next to its `Cargo.toml` and keep `readme.workspace = true` (cargo will use the local copy and drop the relative-path warning).
